# Related Work

Background design references, not extra operating rules.

- **Repository knowledge & memory:** [Harness engineering](https://openai.com/index/harness-engineering/) and [Cline Memory Bank](https://github.com/cline/prompts/blob/main/.clinerules/memory-bank.md) combine thin entrypoints, repo-local knowledge, and agent maintenance. DocDoki keeps those files plain and Git-native without requiring a surrounding platform.
- **Spec-driven systems:** [Spec Kit](https://github.com/github/spec-kit), [Kiro Specs](https://kiro.dev/docs/specs/), and [OpenSpec](https://github.com/Fission-AI/OpenSpec) separate specs from implementation or baseline from change packages. DocDoki separates **design authority** (`specs/`, with optional `status: proposed`) from **execution gaps and evidence** (`work/`).
- **Selective review vs. approval gates:** Tools like Notion MCP's `suggested_edit` separate agent proposals from human acceptance on every edit. DocDoki keeps routine maintenance autonomous and concentrates human review on `overview.md` (`## Open decisions`) and `status: proposed` specs.
- **Context engineering & continuity:** [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents), [Agent Skills best practices](https://agentskills.io/skill-creation/best-practices), and [Long-running agent harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) motivate concise single-source instructions, progressive disclosure, and cold-start work records.
- **Living documentation & verification:** [Living Documentation](https://books.google.com/books/about/Living_Documentation.html?id=8_6ZDwAAQBAJ) and [Skill evaluation guidance](https://developers.openai.com/blog/eval-skills) motivate pairing mechanical validation (`scripts/validate.py`) with representative multi-document lifecycle tasks rather than trusting completion claims.
