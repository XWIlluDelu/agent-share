# Rebuild the code-review skill

从头设计并重写本目录中的 `SKILL.md`。不要把现有 `SKILL.md` 当作模板或设计权威；完成新的综合判断后，直接替换它。

## 宏观需求

这个 skill 用于代码审查，大多数时候审查整个代码库，少数时候审查用户指定的目录、包、模块、功能或其他范围。项目一般不会特别大，因此全库审查应真正覆盖全部相关的一方代码，而不是只抽查热点。

审查重点是：

- 发现代码中证据明确的明显 bug；
- 判断代码组织和架构能否提升可维护性、可理解性，减少耦合与认知负担；
- 找出重复代码、重复概念、多重事实来源、死代码、无价值的抽象和过时兼容路径；
- 当用户明确说明项目由个人或自主小团队控制，或项目材料清楚证明这一点时，允许较激进地建议删除死代码、旧实现和不再需要的兼容设计。没有足够权限证据时保持保守。

审查默认只读。只有用户在调用时预先授权，或在看到审查结果后明确同意，才继续修改代码。

## 重建原则

先重新研究当时公开可得的优秀 code-review、whole-codebase audit、architecture review 和 maintainability review skills，以及相关成熟方法。宁缺毋滥，只选择少数真正契合上述需求、能提供独特判断方法的参考；不要因为旧版本曾引用某个项目就继续沿用它。

综合参考经验和宏观需求，从零写出新的 skill，而不是对旧版本做增量修补。以审查哲学、判断方法和证据纪律为主体，给模型足够的推理空间；避免机械清单、固定发现数量、健康评分、任意行数阈值和过细流程。

每个实质性结论应由可复核的代码位置、调用或触发路径、结构机制及具体后果支撑。区分问题严重程度与证据置信度，重新核对引用，合并共同根因，拒绝偏好型、猜测型和脱离项目语境的意见。保留默认只读和外部状态安全边界。
